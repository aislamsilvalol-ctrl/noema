# Contributing to NOEMA

Thanks for looking. This document is short on ceremony and specific about what makes a
change mergeable here.

## Before you write code

- **Bug fix, small improvement, docs:** open a PR directly.
- **New feature:** open an issue first. Not for gatekeeping — to check it isn't already being
  built, and that it survives the project's one filter: *does this help someone actually
  learn and remember?*
- **Anything touching the learning model** (mastery formulas, FSRS integration, scheduling
  utility, prerequisite logic): open a **discussion**, not an issue. These decisions need
  arguments and ideally evidence. We would much rather debate before the code exists.

## Local development

```bash
git clone https://github.com/aislamsilvalol-ctrl/noema.git
cd noema
cp .env.example .env

# infrastructure only
docker compose up -d postgres redis

# api
cd apps/api
uv sync
uv run alembic upgrade head
uv run uvicorn noema.main:app --reload

# web
cd apps/web
pnpm install
pnpm dev
```

Requirements: Python 3.12+, Node 20+, pnpm 9+, Docker, and [Ollama](https://ollama.com) if
you want to develop without cloud API keys (recommended — most work does not need them).

```bash
make check   # lint + typecheck + tests, everything CI runs
make test    # tests only
make fmt     # format
```

## Standards

**Python.** Ruff (lint + format), mypy in strict mode, pytest. Full annotations on every
public function. `Any` needs a comment explaining why.

**TypeScript.** ESLint, Prettier, `strict: true`. No `any`, no non-null assertions on data
from the network. API types are **generated** from OpenAPI — never hand-write a response
type.

**Commits.** Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`).
The changelog is generated from them.

**Tests.** Bug fixes need a regression test. New engine logic needs unit tests over pure
functions. New endpoints need an API test. Nothing merges with failing CI.

## Architecture rules

These are the constraints that keep the project contributable. A PR that breaks one will be
asked to change, even if the feature is good.

1. **`domain/` and `engines/` stay pure.** No database access, no network, no `datetime.now()`
   — time is a parameter. This is what makes the learning model testable and replayable.
2. **Evidence is append-only.** `reviews`, `answers` and `mistakes` are never updated or
   deleted in normal operation. `concept_mastery` and `card_states` are projections that must
   be rebuildable from them.
3. **No feature code imports an AI SDK.** Everything goes through `providers/gateway.py`.
4. **Nothing generated by AI is persisted unvalidated.** Structured output is schema-checked;
   generated cards and questions require human approval before they become active.
5. **Every AI-produced claim carries provenance.** If it came from a document, it stores the
   chunk ids.
6. **No secret ever reaches a response schema or a log line.** There are tests asserting this;
   do not weaken them.

## Good first contributions

**Add an AI provider.** The clearest entry point. Implement `AIProvider` in
`apps/api/noema/providers/`, declare its `Capabilities`, register it, add contract tests
against the shared provider test suite. One file plus a registry line.

**Add a document parser.** Implement parsing into the shared block IR in
`apps/api/noema/ingestion/parsers/`, add a fixture document and an expected-output test. The
rest of the pipeline is untouched.

**Add a question type.** A payload schema, a deterministic grader, a generation prompt with
eval fixtures, and a renderer.

**Improve the docs.** Especially [`docs/`](./docs) — if something there is wrong, unclear, or
out of date relative to the code, that is a real bug.

## Pull requests

Keep them focused; a 2,000-line PR touching six subsystems will sit unreviewed. Describe what
changed and why, link the issue, include screenshots for UI work, and note any migration.

Every PR runs lint, typecheck, tests and build. AI-touching PRs also run the eval harness
against a deterministic mock provider.

## Reporting bugs and vulnerabilities
